# TraceEagle 进阶教程：用 Diff、请求重放和响应断点排查接口异常

网页能够打开，但切换分页后列表突然变空，该从哪里开始排查？本教程把 TraceEagle 的请求对比、Composer 重放和响应断点串成一个练习，帮助你从“看到请求”进一步走到“验证问题原因”。

本文使用的软件：TraceEagle(XAGNIN5MCAF23Q6WM3N2KJXQ6I)

> 根据 TraceEagle 官方文档整理。接口、数据和故障均为教学示例，不代表实际测评结果。请将示例替换为自己拥有或获准测试的项目；`api.example.test` 是占位域名，不是可直接访问的演示服务。

## 你将练习什么

- 对比正常和异常请求，找到值得验证的差异。
- 使用 Composer 只修改一个参数，检查它是否影响结果。
- 用响应断点模拟空列表，检查前端能否正确处理。
- 把观察结果整理成可复现的问题说明。

## 1. 准备代理抓包环境

本次练习需要修改响应，使用“代理抓包”。启动代理，让测试浏览器经过该代理访问项目；调试 HTTPS 时，根据软件的证书向导完成安装与信任。先确认目标接口的请求和响应已经可读，再开始修改。

具体接入方式见[官方代理抓包说明](https://traceeagle.com/zh/guides/proxy-capture/)。

在测试页面依次打开第一页和第二页，保留两次请求。假设接口为：

```http
GET https://api.example.test/products?page=1&pageSize=20
GET https://api.example.test/products?page=2&pageSize=20
```

记录现象：第一页正常，第二页显示为空。暂时不要把原因归到前端或后端。

## 2. 用 Diff 找到差异

在第一页请求上右键选择“标记为对比 A”，再在第二页请求上选择“与 A 对比”。窗口支持切换请求和响应，并逐行对比报文内容。入口与展示方式见[官方请求对比说明](https://traceeagle.com/zh/guides/compare/)。

建议按这个顺序检查：

| 检查对象 | 关注内容 | 本例的问题线索 |
| --- | --- | --- |
| URL 与查询参数 | 分页、排序、筛选条件 | `pageSize` 是否意外变为 `0` |
| 请求头 | 登录状态、内容类型 | 两次请求是否使用相同测试身份 |
| 响应状态与正文 | 业务错误、空数组、字段结构 | 返回空列表，还是接口已经报错 |

假设你发现第二页实际发送的是：

```http
GET https://api.example.test/products?page=2&pageSize=0
```

这只是一个待验证的线索。真实项目对 `pageSize=0` 可能返回错误、使用默认值，或返回空列表，不能仅凭参数值就断言原因。

## 3. 用 Composer 做单变量验证

选中异常请求，通过“编辑并重发”载入 Composer。先原样发送一次，再仅修改 `pageSize` 重发；发送记录保存在独立的 Composer 会话中，可继续查看和对比。参考[官方请求构造与重放说明](https://traceeagle.com/zh/guides/compose-replay/)。

| 次序 | 操作 | 需要记录 |
| --- | --- | --- |
| A | 原样重放 `pageSize=0` | 是否仍返回空列表 |
| B | 仅改为 `pageSize=20` | 是否返回正常数据 |
| C | 再改回 `pageSize=0` | 空列表是否再次出现 |

三次测试尽量保持测试账号、其他参数和服务端数据不变。如果结果稳定地随该参数改变，就有证据表明它与异常有关。接下来检查分页组件的参数赋值过程，并核对服务端对参数的约定。

如果原样重放已经无法复现，先检查登录是否过期、数据是否变化，以及接口是否依赖动态时间戳或签名。不要同时修改多个字段，否则难以判断是哪项改动起了作用。

## 4. 用响应断点验证空列表场景

参数问题修复后，仍应验证前端是否能处理真实的空数据。在规则中加入以下示例，并替换为自己的测试接口：

```text
api.example.test/products breakpoint://res
```

这条规则按域名与路径前缀匹配，并在响应阶段拦截。重新触发页面请求，命中后编辑响应正文，再点击 `Resume` 放行。断点语法与可编辑字段见[官方规则与断点说明](https://traceeagle.com/zh/guides/rewrite-breakpoint/)。

假设项目原本采用下面的响应结构，只修改列表和总数，保留其他必要字段：

```json
{
  "code": 0,
  "data": {
    "list": [],
    "total": 0
  }
}
```

放行后观察：

- 加载状态是否结束。
- 页面是否展示约定的空状态提示。
- 上一页的数据是否已清除。
- 分页控件是否与当前数据一致。

这一步修改的是本次传给浏览器的响应，不会因此改变服务端保存的数据。若实际接口字段不同，应使用项目自己的结构，避免把结构不匹配误判为空列表处理问题。

## 5. 整理问题记录并回归

关闭临时断点规则，重新执行原始页面操作，确认当前结果没有继续受到响应修改的影响。

可以使用下面的模板记录测试；其中的结论只在实际观察符合时填写：

```text
问题：切换第二页后列表为空。

触发步骤：
1. 打开测试页面，第一页正常显示。
2. 点击第二页。

请求观察：第二页请求的 pageSize 为 0。

验证：
- 原样重放仍返回空列表。
- 仅将 pageSize 改为 20 后返回数据。
- 改回 0 后再次返回空列表。

待检查：分页参数赋值，以及服务端参数校验约定。

回归范围：第一页、第二页、末页、空列表、切换筛选条件后的分页。
```

发布问题记录或截图前，移除其中的真实 Cookie、Token 和个人数据。附上必要的请求参数、响应差异与复现步骤，便于其他开发者验证。
